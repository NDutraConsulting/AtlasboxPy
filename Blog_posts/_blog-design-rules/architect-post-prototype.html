MCP Is for Strangers

A protocol for crossing a boundary you don't control gets reached for by default now, even when there's no boundary to cross.

Platform & Architecture · 29 Aug 2026 · 11 min read · references 3 ADR proposals

Every agent we've shipped this year has needed to call at least one tool that already lives in our own codebase. The reflexive answer for "how does it call that tool" has increasingly been MCP — and increasingly, that reflex has been wrong. Not because MCP is bad, but because it solves a narrower problem than the reflex assumes: crossing an ownership boundary, a different team, a different company, a different runtime. Most of our agents never cross one.

This post walks through two decisions that follow from that observation, and how they relate. The first draws the line for when MCP is actually worth its cost. The second decides what should replace it when it isn't — which turns out to already exist in how every other caller reaches our systems today.

ADR AD-014

Reserve MCP for Genuine Ownership Boundaries

main @ a3f9c1e Proposed
Problem
Agents are treated as a category that always needs MCP, even when the tool they're calling already lives in the same codebase, language, and deploy as the agent itself.
Solution
Call internally-owned tools directly through the existing validator_gateway call path. Reserve MCP for tools that genuinely cross an ownership boundary — a different team, a different company, or multiple independent clients.

improves trade-off to watch

Cognitive Load

Lower for the common case: one call path, typed response, instead of holding a protocol schema and a function signature in sync. Rises only if a tool later needs external discovery — added deliberately, not by default.

Performance

Removes a serialization and IPC hop from the agent's reasoning loop. A tool call behaves like any other function call in-process — no round trip, no JSON-RPC overhead, no server startup latency on first use.

Reliability

Neutral to positive, conditional on discipline. Calls inherit the gateway's shared error taxonomy and recovery policy instead of per-agent retry logic. Regresses only if a team bypasses the gateway for an undisciplined direct call.

Evolvability

Slight deferred cost: no built-in dynamic discovery if a second, independent consumer later needs this tool. Mitigated cheaply — wrap the same controller in an MCP server when that boundary actually appears.

Decision Rule

✓

Same codebase, runtime, and owner → call it directly through the gateway. No server, no schema, no protocol.

✗

Different team, company, or multiple independent clients need the same tool → MCP is earning its keep. Build the server.

Rough secondary signal: fewer than about three independent integrations sharing a tool means the N-to-M problem MCP exists to solve hasn't shown up yet.

A Context ›

Agents are now a normal category of caller into our systems, alongside REST clients and background workers. The default answer for "how does an agent reach a tool" has become MCP — stand up a server, describe the tool as a schema, give the agent a client.

That default isn't wrong in general. MCP solves a specific problem: letting a client discover and invoke a tool it doesn't own, across a boundary a standardized protocol genuinely helps cross. The friction shows up when that reflex gets applied uniformly, including to tools that were never on the other side of any such boundary.

B Rationale & Evidence ›

The cost side isn't speculative. Independent write-ups across the industry converge on the same short list of costs when MCP is applied where no ownership boundary exists: added latency from serialization and IPC now sitting inside the reasoning loop, added complexity from turning a function call into a network call, reduced observability, and ongoing operational toil from every server becoming another artifact to keep alive.

We're not the only ones drawing this line. AMD's robotics research team published a physical-AI agent architecture on 25 Aug 2026, calling the robot's existing ROS 2 perception, planning, and control capabilities directly as tools — not through an added protocol layer, justified by interpretability and on-device latency. They take no position on MCP either way; this is a production team's revealed preference, not an opinion. Read the source →

C Consequences ›
What gets easier
  • No new server to deploy or keep alive for tools we already own.
  • Failures surface in the same stack trace and error taxonomy for every caller.
  • Agents inherit whatever recovery policy is already attached to the gateway, for free.
What we give up
  • No built-in dynamic discovery if a future external consumer needs this tool.
  • Only sound if the gateway is actually adopted, not bypassed.
D Alternatives Considered ›
  1. MCP by default for all agent tool calls. Rejected — pays the full protocol cost on tools that never cross a boundary.
  2. Undisciplined direct calls, no shared infrastructure. Rejected — reintroduces inconsistent error handling.
  3. Direct calls through the gateway; MCP reserved for genuine boundaries. (Chosen.)
E When to Revisit ›
  • A tool used only by our agents needs a second, independent consumer — wrap the controller in an MCP server without touching the implementation.
  • Independent clients needing a given tool cross roughly three.

AD-014
  └─ AD-014.1  extends — what replaces MCP when we opt out

Drawing that line raises an immediate follow-up: if agents aren't going through MCP for internal tools, what exactly are they calling instead? That's less a new question than an existing answer — the same call path our REST routes and workers already use, formalized as a second, dependent decision.

ADR AD-014.1

Extend the Gateway as the Default In-Process Call Path for Agents

main @ a3f9c1e Proposed
Problem
Opting out of MCP for internal tools only helps if "call it directly" doesn't quietly become "call it however each agent's author feels like" — inconsistent error handling, no shared observability, no retry logic.
Solution
Any in-process agent constructs the same ValidatorGateway around the same controller a REST route or worker would use, and calls .handle() directly — never the raw controller method.

improves trade-off to watch

Cognitive Load

Zero new concept for engineers who already know the gateway from REST and worker call sites — an agent is just another caller, not a new abstraction to learn.

Performance

No overhead beyond the gateway's own try/except and formatting logic, already in the hot path for every other caller today.

Reliability

Agent-originated failures get retry, redirect, or queue behavior for free by attaching a recovery policy to the gateway instance — important since agents run unattended and won't notice a silent failure.

Evolvability

If an agent's tool later needs to become a publicly discoverable capability, the same controller wraps in an MCP server without changing the underlying business logic.

Decision Rule

✓

Agent calls a controller it owns → construct ValidatorGateway(controller), optionally attach a RecoveryEngine, call .handle().

✗

Agent calls the controller method directly, or wraps it in bespoke error handling → not compliant with this decision.

A Consequences ›

Every caller — REST route, worker, or agent — now produces identical, typed success and error responses for the same controller. Debugging an agent failure means reading the same error taxonomy an engineer already knows from the REST logs, not a separate agent-specific format.

AD-014.1
    └─ AD-014.1.1  extends — closes a gap AD-014.1 opened, on the agent-runtime fork

AD-014.1 removed the network hop, but it also removed the one thing MCP would have given agents for free: a negotiated schema. A controller's method signature can change, and a direct call has no protocol to warn the caller. That gap surfaced for real once the agent-runtime fork started iterating on controller interfaces faster than the rest of the codebase — which is what produced a third, more specific decision.

ADR AD-014.1.1

Require a Deprecation Window Before Changing Any Agent-Callable Controller Method

agent-runtime @ f6b21d0 Proposed
Problem
Direct in-process calls (AD-014.1) give agents no protocol-level interface negotiation — unlike MCP's schema discovery, a controller's method signature can change and break an agent silently on its next call.
Solution
Any controller method reachable by an agent must carry a minimum deprecation window — old and new signatures coexist for at least one release cycle — enforced via a static agent-callable registry checked at review time, not a runtime protocol.

improves trade-off to watch

Cognitive Load

Adds one habit for engineers changing a controller: check the agent-callable registry before renaming or removing a method. Small, but real — MCP would have made this a schema diff instead of a manual check.

Performance

No runtime cost — the registry check happens at review and CI time, not on the call path. Agents keep the zero-hop performance AD-014.1 already established.

Reliability

Directly closes the gap AD-014.1 opened: an agent can no longer be broken by an unannounced signature change on a controller it calls directly.

Evolvability

Slightly slower to remove old controller methods than an unconstrained codebase would allow, in exchange for agents never silently breaking on a change they had no way to see coming.

Decision Rule

✓

Changing a controller method's signature and it appears in the agent-callable registry → deprecate first, remove next release cycle.

✗

Method isn't in the registry → normal change process, no window required.

A Consequences ›

Every agent-callable controller method now has exactly one place its callers can be checked before a breaking change ships — the registry — rather than relying on whoever's changing the method to remember which agents might depend on it.

Keep it strategically simple

Skipping the protocol layer isn't the lazy choice, it's the considered one — made after checking whether the boundary the protocol exists to solve is actually there. Most of the time, for most of our agents, it isn't. Presenting these decisions together, rather than as separate entries in a flat ADR list, is deliberate: seeing AD-014.1.1 branch from AD-014.1 branch from AD-014 tells a reader not just what we decided, but why one decision made the next one necessary — and the version badge on each node tells them which state of the system that necessity showed up in.
